# 生命周期与过期策略（Task 7）

## 1. 三条不可协商的前提

1. **到期 ≠ 失效。** `review_after` 到期只是把笔记放进 `recheck --due` 的候选列表，
   由人或 Agent 重新判断。工具**绝不**自动改 `status`，**绝不**删除任何文件。
2. **基准日必须显式传入。** 所有函数接收 `base_date` / `today`，内部不读宿主时区的隐式 today。
   否则同一份笔记在武汉和 UTC 的机器上会算出不同日期。
3. **证据不足不猜。** 时效分级判断不出来就返回 `evolving`，不为了「显得聪明」判 `stable`。

## 2. 复核周期

| 内容时效 `content_volatility` | 默认周期 | 适用 |
|---|---|---|
| `stable` | 365 天 | 制度、标准、红线、可长期复用的判断原则 |
| `evolving` | 90 天 | 默认档；在演进但未定型的结论 |
| `volatile` | 30 天 | 临时方案、还在试、随时可能被推翻 |
| `progress` | 14 天 | 进度快照，只在短期内可信 |

- `review_after = base_date + 周期`，用 `date + timedelta`，跨月/跨年/闰年由标准库处理。
- 周期常量在 `lifecycle.DEFAULT_REVIEW_DAYS`。**本版本没有 config 级覆盖开关**：
  `AppConfig` 里没有 `policy` 字段，读到未知配置键也不会生效（见 `references/config.md`
  的字段表）。需要不同周期，只能在调用 `compute_review_after` 前自行传入或改代码。

## 3. 可检索性

| 状态 | 默认检索 | `--include-stale` |
|---|---|---|
| `有效` | 是 | 是 |
| `待复核` | 是（优先级降低） | 是 |
| `已过时` | 否 | 是 |
| `已被取代` | 否 | 是 |

- 未知状态**报错**，不猜测。把不认识的状态当成「可检索」或「不可检索」都是替用户做决定。
- `待复核` 可检索，但排序应该靠后；**不要仅因 `review_after` 到期就把它判成已过时**。

## 4. 时效分级的确定性口径

`classify_volatility(project, decisions, title)` 只看关键词命中，不做语义理解：

| 类别 | 关键词（示例） | 判定门槛 |
|---|---|---|
| 进度 | 进度、进展、当前状态、已完成、已跑完、本轮、第一/二/三轮、今日、本周 | 命中 ≥ 2 个**不同**词，且不少于另两类 |
| 易变 | 临时方案、尚未确定、待定、实验中、试运行、可能变化、不稳定、还在试、待验证 | 命中 ≥ 2 个不同词，且多于稳定类 |
| 稳定 | 规范、标准、原则、契约、协议、红线、方法论、长期有效、不可协商、硬性要求 | 命中 ≥ 2 个不同词，且多于易变类 |
| 兜底 | —— | 其余情况一律 `evolving` |

- 判定顺序：进度 → 易变 → 稳定 → 兜底。进度优先，因为「走到哪一步」的信号最强。
- 同一个词重复出现只算一次（「进度」写十遍不等于证据更强）。
- 门槛设在 2 个不同词，是为了避免「这条笔记里出现了一次『标准』就判 stable」这种误判。
- 这是**建议值**，不是结论：蒸馏时可以覆盖；分级只影响默认复核周期，不影响笔记内容。

## 5. 与写入/检索的接线

- `compute_review_after(valid_from, volatility)` 提供「按周期算日期」这个能力，但**目前没有
  接入归档主链路**：`writer.py` 直接写 `DistilledNote.review_after`，只校验 `YYYY-MM-DD` 格式，
  不会用 `content_volatility` 重算覆盖。要让它生效，必须由蒸馏端（人或 Agent）按上面的周期
  算好再填进 `review_after`。
- 写入时：`content_volatility` 决定 frontmatter 的 `内容时效` 标签；`review_after` 原样落盘。
- 检索时：`iter_notes(config, include_stale=False)` 只返回 `有效` / `待复核`。
- 复核时：`recheck --due` 用 `is_due(review_after, today)` 列出候选，**只列不改**。
